### 1. GitLab Workflow & Branching Strategy

We will use a **Feature Branch Workflow** enforced via GitLab Protected Branches.

#### **Branch Hierarchy**
1.  **`main` (Protected):** Production-ready code. Deploys to live/demo environment.
2.  **`develop` (Protected):** The integration branch. All features merge here for testing.
3.  **`feature/...`:** Temporary branches for new capabilities.
4.  **`fix/...`:** Bug fixes.

#### **Naming Conventions**
* **Branches:** `type/component-description`
    * Examples: `feature/fe-auth-login`, `feature/be-rag-ingestion`, `fix/be-sync-timestamp`
* **Commits:** `[Component] Action - Description`
    * Examples: `[FE-Chat] Add microphone permission logic`, `[BE-Quiz] Fix JSON parsing in Ollama response`

#### **Merge Request (MR) Rules**
* **Approvals:** Minimum 1 peer review required (Frontend reviews Frontend, Backend reviews Backend).
* **CI Pipeline (Recommended):**
    * *Frontend:* ESLint check + Build test.
    * *Backend:* Flake8/Black check + Pydantic model validation.
